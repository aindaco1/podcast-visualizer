# Podcast Visualizer 1.0.1 execution plan

Status: approved for implementation on 2026-08-08.

Branch: `release/1.0.1`

This document is the authoritative scope, sequencing, and release gate for
Podcast Visualizer 1.0.1. It supersedes conversational notes. The 1.0.0
product and release contracts remain in force unless this plan explicitly
changes them.

## Outcome

Release a signed and notarized 1.0.1 update that improves transcript quality,
review ergonomics, revision safety, default output choices, update placement,
and artifact size without weakening the local-first architecture or silently
overwriting any existing project stage or render.

The release must:

- produce cleaner transcript drafts for common English capitalization and year
  forms while preserving raw Parakeet evidence;
- avoid avoidable one-word cue tails through deterministic, bounded grouping;
- let users reopen and revise an already approved or rendered transcript by
  creating a new immutable revision;
- navigate literal transcript matches and replace either the selected match or
  every match;
- default new render selections to Landscape 16:9, Opaque H.264, and Compact
  HEVC Alpha;
- expose Check for Updates in persistent top-left window chrome;
- reduce full-install and update download cost while retaining bundled,
  verified runtimes; and
- pass source, security, performance, signing, notarization, Sparkle, and clean
  installation gates before publication.

## Non-negotiable engineering rules

- Media, transcripts, model inputs, and review data remain on the Mac.
- Models remain explicit, hash-verified imports. There are no implicit model
  downloads.
- The app does not depend on Homebrew, ambient `PATH`, system Node, system
  Python, system FFmpeg, or developer tools.
- Existing source media, approved revisions, alignment evidence, scenes,
  renders, and release artifacts are never silently overwritten.
- Subprocesses use executable URLs plus argument arrays and never a shell.
- Every new or changed trust-boundary contract rejects unknown fields,
  traversal, symlink escapes, unsafe identifiers, invalid bounds, and
  non-canonical hashes.
- Every behavioral fix and contract change includes automated regression tests.
- Performance and artifact-size work starts from a recorded baseline and is
  accepted only after remeasurement.
- Generic timed-text normalization, matching, cue grouping, revision lineage,
  and alignment behavior belongs in a shared package. App-specific workflow,
  window chrome, and release policy stay in this repository.

## Baselines to preserve

The 1.0.0 release is the compatibility baseline:

- Published Sparkle ZIP: 381,771,149 bytes.
- Published DMG: 609,877,439 bytes.
- Local assembled app: approximately 1.18 GiB on disk.
- Bundled alignment runtime: 979,430,596 logical bytes across 31,364 files;
  approximately 270.7 MB under streaming gzip measurement.
- Bundled Node: 121,306,800 bytes; approximately 39.0 MB compressed.
- Runtime architecture: Apple Silicon arm64.
- Project/review schema compatibility: existing reviewed transcript revisions
  v1 and v2 and existing projects without an active-revision pointer.

Record functional and timing baselines before changing each applicable
subsystem. Store reproducible benchmark commands and fixtures in tests or
release documentation; do not commit private podcast media.

## Workstream 1: deterministic transcript editorial normalization

### Contract

Add one pure, deterministic English editorial-normalization pipeline. Preserve
the raw Parakeet response as immutable analysis evidence and apply normalized
display text only when constructing the editable review draft.

The pipeline owns ordered rules for:

- standalone lowercase `i` and common contractions such as `i'm`, `i've`,
  `i'll`, and `i'd`;
- sentence-initial capitalization where punctuation provides an unambiguous
  boundary;
- conservative English year forms in the supported 1900–2099 range, including
  forms such as `twenty twenty four` and `two thousand twenty four`; and
- whitespace cleanup required by those transformations.

It must not paraphrase, remove filler words, alter speaker labels, fabricate
punctuation, or change raw model tokens/timings. Each normalized display token
must retain a deterministic mapping to the spoken/raw token span used for
review and later alignment.

### DRY ownership

Put generic token/text normalization and spoken-to-display mapping in the
shared timed-text package. Keep the product's lightly-cleaned-verbatim policy
and rule-set version selection in Podcast Visualizer.

### Acceptance tests

- Positive and negative year fixtures, including ambiguous number phrases.
- `i`/contraction capitalization at beginnings, middles, and punctuation
  boundaries.
- Unicode punctuation and apostrophe variants.
- Stable output and hashes across repeated runs.
- Raw evidence remains byte-for-byte unchanged.
- Alignment projection still covers every approved spoken word.

## Workstream 2: bounded, intelligent cue grouping

### Contract

Replace greedy line/cue grouping with a deterministic bounded optimizer that
scores a small candidate window using:

- punctuation and sentence boundaries;
- meaningful silence and diarization turn boundaries;
- target/minimum/maximum readable word counts;
- measured or bounded character width; and
- an orphan penalty that avoids a one-word tail when a legal rebalance exists.

Hard timing, speaker, maximum length, and validation boundaries always beat
cosmetic grouping. A genuine one-word utterance remains valid. The algorithm
must be O(n * k) with a fixed, documented maximum candidate window `k`; it may
not use unbounded backtracking or quadratic transcript-wide rescans.

### DRY ownership

The optimizer and scoring primitives belong in the shared timed-text package.
Podcast Visualizer owns its target thresholds and editorial preset version.

### Acceptance tests and performance gate

- Punctuation, pause, speaker-change, short final cue, and unavoidable singleton
  fixtures.
- Deterministic grouping from identical timed tokens.
- No cue overlap, duration overflow, word loss, or word duplication.
- Establish the 1.0.0 grouping baseline on synthetic 5-, 30-, and 120-minute
  transcripts; the new implementation must remain linear in token count and
  within the measured regression budget before merge.

## Workstream 3: immutable post-approval revisions

### Contract

Approved transcripts remain immutable. Editing an approved, aligned, rendered,
verified, or exported project creates a new working copy whose parent is the
currently active approved transcript. Approval creates a new content-addressed
review revision and atomically advances a small validated active-revision
pointer. It never edits or deletes the parent revision, alignment, scene,
render, or output.

The active pointer must bind to the project, prepared audio hash, transcript
ID, parent transcript ID when present, and revision hash. Pointer replacement
must be atomic and symlink-safe. Downstream alignment and rendering resolve the
active transcript explicitly and create new content-addressed outputs.

Existing projects migrate as follows:

- one legacy approved revision and no pointer: validate it and establish it as
  active when a new edit or approval requires a pointer;
- no approved revision: continue the draft-review path;
- multiple legacy approved revisions and no unambiguous active selection: do
  not guess or overwrite; return a corrective error while leaving all evidence
  intact.

The app must provide an Edit Transcript action after approval and after
verification. Opening the Transcript Review tab must load the active revision
as an editable working copy. Approving the new revision returns workflow state
to approved and automatic continuation may align and render it without an
extra button when all required render choices are already present.

### DRY ownership

Revision lineage, canonical hashing, active-pointer validation, and migration
helpers belong beside shared reviewed-transcript contracts. CLI commands own
project I/O and atomic persistence. Swift owns typed presentation and invokes
the CLI rather than duplicating persistence rules.

### Acceptance tests

- Edit after approved, aligned, verified, and exported states.
- Parent remains byte-for-byte unchanged.
- New transcript/alignment/render IDs change when content changes.
- Unchanged expensive analysis stages are reused.
- Legacy v1/v2 projects reopen correctly.
- Ambiguous legacy lineage fails safely without mutation.
- Interrupted pointer writes cannot leave a partially valid pointer.

## Workstream 4: Transcript Review match navigation and replacement

### Contract

Create one literal, Unicode-safe matching engine used by match counts,
Previous, Next, Replace This, and Replace All. A query may be a character, word,
or phrase. Options remain Match case and Whole words.

Matches are represented with stable cue IDs and UTF-16 ranges compatible with
macOS text selection. Search remains cue-local so replacement never silently
crosses a timing boundary; users can Merge Next before replacing a phrase that
spans cues.

UI behavior:

- show Previous and Next controls plus `current of total`;
- wrap at the first and last match;
- scroll to, focus, and visibly select the current match;
- support Command-G and Shift-Command-G while Transcript Review is focused;
- Replace This replaces only the current validated range and advances to the
  next sensible match;
- Replace All uses the exact same matcher and options;
- edits, cue merges, speaker operations, and query changes invalidate stale
  descriptors safely; and
- replacement participates in the review's dirty state and Undo behavior.

Use native SwiftUI text selection when it reliably exposes the required range.
If it does not, introduce only a narrow `NSViewRepresentable`/`NSTextView`
boundary. SwiftUI remains the source of truth; the AppKit coordinator may own
only responder, selection, and delegate glue.

### Acceptance tests and performance gate

- Character, word, phrase, case-sensitive, whole-word, Unicode, emoji, and
  composed-grapheme fixtures.
- Navigation wrapping and empty/no-result behavior.
- Replace This and Replace All produce identical matching semantics.
- Stale selection after merge, edit, delete, or query change cannot corrupt a
  different range.
- Establish search/reindex latency on a 10,000-cue synthetic workspace. Keep
  UI work bounded and avoid a transcript-wide rescan on unrelated speaker-only
  changes where practical.

## Workstream 5: persistent top-left update action

Remove the custom Podcast Visualizer menu's Check for Updates entry. Add one
visible Check for Updates action to the leading window toolbar so it remains in
the top-left for both Project and Transcript Review tabs. It must use the
existing Sparkle controller, disabled-state contract, accessibility label, and
help text; it must not introduce a second updater or general app networking.

Keep Open Project and Choose Source commands in their existing desktop command
locations. Do not register duplicate shortcuts or duplicate updater actions.

Acceptance requires a Swift build, controller unit coverage where practical,
and a signed-app smoke test that exercises Sparkle from both tabs.

## Workstream 6: default render selections

New app sessions and newly opened projects default to exactly:

- Landscape 16:9;
- Opaque H.264; and
- Compact HEVC Alpha.

Square, Vertical, and ProRes Alpha remain available but unselected. Persisted
explicit choices, if introduced later, must not be overwritten by defaults.
Command construction remains centralized in `RenderSelection` and emits the
minimum deterministic invocation set without duplicate renders.

Acceptance tests cover default state, toggling, validation, CLI argument
construction, and reopening a project.

## Workstream 7: self-contained size and update efficiency

### Required low-risk 1.0.1 changes

1. Build/stage a production-only alignment environment and omit verified
   non-runtime content such as development dependencies, test trees, type
   stubs, Python/PyTorch headers, and compiler tooling. Use an allowlisted,
   reproducible staging policy; do not hand-delete arbitrary package files.
2. Strip local symbols from the Node and Swift executables before runtime
   hashing, nested signing, and notarization. Regenerate manifests after every
   byte-changing operation.
3. Package the DMG with ULFO/LZFSE instead of default UDZO level 1. The local
   baseline produced approximately 497.4 MB from the current app bundle.
4. Generate and publish signed Sparkle binary deltas from the prior stable ZIP.
   Download prior archives only over HTTPS, verify their pinned GitHub digest
   and SHA-256 before use, cap retained versions/deltas, and upload only the
   generated current-release delta artifacts. Keep the full signed ZIP as the
   fallback.
5. Record installed app, ZIP, DMG, and delta bytes in release metadata and fail
   CI on an unexplained budget regression.

The conservative prototype target is a full ZIP no larger than 355 MB and a
DMG no larger than 510 MB, subject to final signed/notarized measurement. A
larger result requires documented evidence rather than silently relaxing the
budget.

### Gated higher-value prototype

The application invokes only WhisperX forced alignment with a pinned
torchaudio Wav2Vec2 model, while the current environment includes WhisperX's
ASR and diarization dependency closure. Prototype a purpose-built alignment
path in the shared alignment runner that avoids unused imports and locks only
the packages required for this product path.

Synthetic archive measurement reduced the alignment payload from about
270.7 MB to 118.9 MB and suggests a 225–235 MB full ZIP. This is not permission
to delete packages from the current runtime. Ship the narrow runtime in 1.0.1
only if:

- golden word timing, confidence, and unaligned-reason fixtures match the
  reviewed contract;
- the 98% quality gate and representative long-form alignment pass;
- cold start, peak RSS, and wall time meet the measured baseline budget;
- offline execution, manifest verification, licenses/SBOM, nested signing,
  notarization, and Gatekeeper pass; and
- the shared runner remains the single source of alignment behavior.

If any gate fails or results are ambiguous, retain the conservative runtime in
1.0.1 and schedule the narrow runtime for 1.1.0.

### Explicitly rejected shortcuts

- Homebrew or ambient runtime dependencies.
- Downloading executable runtimes on first launch.
- Removing required licenses, model verification, Sparkle services, or security
  evidence for cosmetic size savings.
- Filesystem compression tricks that make code-signing or installation
  behavior less predictable.

## Workstream 8: security and privacy verification

Threat model the new surfaces before release:

- transcript input may contain hostile Unicode, regex metacharacters, control
  characters, or oversized content;
- project directories and revision pointers may contain traversal or symlink
  attacks;
- prior release archives used for Sparkle deltas are untrusted until digest
  verification;
- packaged Python/Node/FFmpeg trees are executable supply-chain inputs; and
- updater traffic is a separate, signed Sparkle boundary rather than general
  app networking.

Required checks:

- literal matching escapes all pattern syntax and validates stale UTF-16
  ranges before replacement;
- JSON contracts remain bounded and reject unexpected fields;
- canonical hashes and content-addressed IDs are recomputed at trust
  boundaries;
- temporary review files are private, bounded, and removed on completion;
- no media/transcript/model path is sent to a network API;
- all executable dependencies are pinned, inventoried, licensed, hashed, and
  signed inside-out; and
- secret scanning, dependency audit, entitlements comparison, notarization,
  stapling, and Gatekeeper checks remain release blockers.

## Workstream 9: performance verification

Measure before and after; do not accept subjective performance claims.

Record at least:

- normalization and grouping wall time versus token count;
- Transcript Review load, search index, next/previous, replace-one, and
  replace-all latency on small and 10,000-cue workspaces;
- memory behavior while editing and searching a long transcript;
- alignment cold start, wall time, and peak RSS if the runtime changes;
- render wall time, peak RSS, streaming behavior, and A/V drift for the
  representative long render; and
- installed app, ZIP, DMG, and Sparkle delta bytes.

Use medians plus worst observed samples for deterministic local benchmarks.
Add regression thresholds only after recording the baseline. Long renders must
continue streaming and must not create image-sequence intermediates.

## Implementation order

1. Capture current functional, performance, and artifact baselines.
2. Add shared normalization and cue-grouping contracts and tests.
3. Integrate normalized review drafts and new grouping without changing raw
   analysis evidence.
4. Add immutable revision lineage, active selection, migration, and CLI tests.
5. Expose post-approval editing and automatic downstream continuation in Swift.
6. Add the shared review matcher, navigation, selection, replace-one, and undo.
7. Move the updater to persistent leading toolbar chrome.
8. Lock the render defaults.
9. Implement conservative artifact-size and Sparkle-delta improvements.
10. Evaluate the narrow alignment runtime against its explicit ship/no-ship
    gate.
11. Run all source, security, migration, UI, performance, signing, packaging,
    and clean-install gates.
12. Update version metadata, changelog, release notes, SBOM inputs, and handoff.
13. Commit and push the release branch, merge only green reviewed source,
    create an immutable signed `v1.0.1` tag, and publish through the protected
    GitHub release environment.
14. Download every published artifact into an empty directory, verify
    checksums, assess Gatekeeper, install the DMG, and update from 1.0.0 through
    Sparkle including the delta path and full-ZIP fallback.

## Source gates

Run from a clean recursive checkout:

```bash
npm ci --ignore-scripts
npm audit --omit=dev --audit-level=high
npm run check
npm run test:coverage
swift test --package-path macos --disable-automatic-resolution
git diff --check
```

Also run the shared timed-text and alignment-runner gates for every changed
submodule, verify recursive submodule status, and ensure no source media, model
weights, credentials, private review data, or build output is staged.

## Release gates

- Version `1.0.1` agrees in `package.json`, `Info.plist`, changelog, release
  notes, tag, app bundle, appcast, checksums, SBOM, and build metadata.
- The exact assembled arm64 app verifies all runtime/model manifests and has no
  dependency on Homebrew, `/usr/local`, the repository, or an ambient runtime.
- All nested Mach-O code is inventoried and signed inside-out with reviewed
  entitlements. `codesign --deep` is verification-only, never the signing
  method.
- App and DMG notarization, stapling, Gatekeeper assessment, quarantine launch,
  output generation, and project reopening pass.
- The signed appcast includes the full ZIP and a valid 1.0.0-to-1.0.1 delta,
  and an intentionally corrupted archive/delta is rejected.
- Published assets match `SHA256SUMS`; release provenance contains no secrets
  or private paths.
- Existing 1.0.0 projects and renders remain intact after opening and after
  creating a new transcript revision.

## Definition of done

1. Every workstream's acceptance tests are automated and green.
2. The conservative size/update changes ship; the narrow alignment runtime
   ships only if every gate passes.
3. Documentation and user-facing release notes accurately describe behavior
   and requirements.
4. The source branch and submodule pointers are clean, reviewed, committed, and
   pushed.
5. The signed/notarized 1.0.1 GitHub release is published with verified assets.
6. A 1.0.0 installation successfully discovers, verifies, installs, and
   relaunches 1.0.1 through Sparkle.
